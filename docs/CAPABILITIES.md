# Installed CLI capability map

Target verified during implementation: Apple `container` 1.5.0, arm64, macOS 26.6, Homebrew Cellar path `/opt/homebrew/Cellar/container/1.5.0`. The command map uses the installed `container --experimental-dump-help` JSON (including command option/flag kinds, preferred spellings, repeatability and positionals), installed zsh/fish completions, and direct help from bundled Compose/Kubernetes plugins. The installed binary is authoritative when release docs and completions disagree. Advanced Command uses typed controls for the installed option set; required arguments and repeatable inputs are modeled separately. Archive operations require explicit file paths so tar bytes are not misread as text output.

## Global command groups

The installed root CLI completion exposes these command groups: `clean`, `copy`, `create`, `delete`, `exec`, `export`, `inspect`, `kill`, `list`, `logs`, `run`, `start`, `stats`, `stop`, `prune`, `build`, `image`, `registry`, `machine`, `volume`, `builder`, `network`, `system`, and `help`.

Installed nested groups:

- `image`: `delete`, `inspect`, `list`, `load`, `prune`, `pull`, `push`, `save`, `tag`.
- `registry`: `login`, `logout`, `list`.
- `machine`: `create`, `delete`, `inspect`, `list`, `logs`, `run`, `set`, `set-default`, `stop`.
- `volume`: `create`, `delete`, `list`, `inspect`, `prune`.
- `builder`: `start`, `status`, `stop`, `delete`.
- `network`: `create`, `delete`, `list`, `inspect`, `prune`.
- `system`: `df`, `dns`, `kernel`, `logs`, `property`, `start`, `status`, `stop`, `version`.
- `system dns`: `create`, `delete`, `list`.
- `system kernel`: `set`.
- `system property`: `list`.

The app does not invent `container commit` or remote machine contexts; neither is supported by the installed 1.5.0 binary. Compose/Kubernetes are plugins, not core CLI groups.

## Safety and data handling

- Profiles are stored as versioned JSON at `~/Library/Application Support/ContainerDesk/environment-profiles.json`, with private permissions and atomic replacement. An unreadable or externally changed library blocks writes until explicit reload; stale editors cannot overwrite a changed/deleted profile. Limits are 200 profiles, 2 MiB per library and 128 KiB per import/export. Unknown schema fields/versions and nonregular or symlink input files are rejected.
- Profiles never store the Run form's inline environment values. Saving records those keys as required names; launch requires them in explicit overrides or referenced files. Environment files are bounded to 1 MiB each and read once into transient redacted argv values before launch, avoiding a second read with different contents. Command strings and local paths are saved as entered; users should keep credentials in environment files or transient overrides and review commands/paths before export. Imported profiles always get fresh IDs and unique names, and require a separate reviewed Run action.
- Every command is executed as an argv array; no shell expansion is used for app forms.
- Advanced Run/Create/Exec/Machine Run snapshot environment-file and inherited values into transient redacted arguments, using the same bounded file reader as normal launches. Reviewed resource actions retain their original CLI identity and require renewed review after a Settings change. Forced post-mutation refreshes wait for a newer inventory attempt.
- Registry passwords go to stdin; the login form keeps the password only in transient view state, clears the field after success or failure, and never writes it to Activity. Environment values, build args, build secret descriptors, and inspect environment payloads are redacted from previews, streamed output and visible inspect JSON where applicable.
- Workspace list JSON is reduced to curated resource summaries. Advanced structured container lists are rendered as redacted JSON only after a complete bounded document is available; failed, malformed or oversized documents stay hidden. Kubernetes list is plain output and never passed to a JSON parser. Limits recreation is an explicit exception to transient configuration handling: its private recovery metadata retains the full launch configuration, including environment values, so settings can be restored. Those values never appear in its UI or Activity.
- Edit Limits validates the reviewed identity, configuration and state before mutation, copies and hashes the stopped writable disk and boot files before deleting the old container, and checks the recreated configuration and prior running/stopped state. Existing named volumes and bind sources are reused, not copied or deleted. Recovery files remain under `~/Library/Application Support/ContainerDesk/LimitsRecovery` with private directory/file modes; they may be boot dependencies and must not be removed while the recreated container exists. The flow refuses unsupported or unsafe configurations, including auto-remove and tmpfs mounts, and attempts rollback after a failed replacement. The guest TTY setting is preserved; attached terminal sessions, process memory and ephemeral network state are reset.
- User-targeted destructive operations have a confirmation step. System stop, cluster delete, Compose down, pruning and registry logout state their scope.
- Activity retries use a conservative read-only command allowlist. Mutating commands cannot be replayed from Activity after failure; their original flow must be reopened for a fresh submission. Process output and Activity relay queues are bounded, and overflow cancels the owned operation with an explicit error.
- Never-started stopped containers can change limits without booting. The cold path preserves their image filesystem reference, full settings and existing mounts, and retains verified boot-file recovery copies. Missing or inconsistent boot artifacts on a previously started container are rejected before deletion.
- Cleanup is an explicit manual workflow: users review the exact candidates and confirm a frozen selection; the app revalidates and removes targets one at a time, then verifies exact target absence. Plugin-owned containers are excluded so dedicated plugin teardown can remove associated state. Stopped container writable-layer data and volume data are permanently deleted when those resources are removed. Volumes are excluded from the default selection. No cleanup action invokes bulk pruning.
- Quitting the app does not stop the Apple container service, containers, machines, Compose projects or Kubernetes clusters.
- Quitting does cancel in-progress MLX downloads and chat requests and waits for only ContainerDesk-owned MLX servers to stop. App-owned server logs and downloads are transient; each window and server session has separate chat history, bounded in memory and never written to preferences or Activity. A model download requires an explicit repository ID; the app does not install Python or MLX-LM.
- Imported-folder models offer **Forget Reference**, which removes only the stored path. Hugging Face cache files are never deleted. **Move to Trash** is limited to app-managed downloads after Core verifies the managed-model manifest and path; the action is blocked while the model has an active server.
- Changing the managed models folder retains the catalog records used by active owned servers until they stop, keeping their lifecycle controls reachable.
- Each model has at most one active app-owned server. Completed sessions release their execution handles and finish event subscriptions. Recent diagnostics retain one inactive session per model and at most eight inactive sessions overall; older output and chat state are discarded. Conversations belong to a window and server session: changing views cancels generation while retaining history, closing a window clears its chat state, and a new server session starts a new conversation.

## Disposable plugin smoke harness

`script/plugin_smoke_test.sh` runs Compose up/down with matching dry-run flags and an isolated K8s create/list/load-image/write-config/delete flow. It generates a unique Compose project and cluster name, passes a temporary `KUBECONFIG` to every K8s command, writes `k8s write-config` to a second temporary path, and verifies the default `~/.kube/config` SHA-256 is unchanged. K8s image loading requires an image that already exists locally (`CONTAINERDESK_K8S_IMAGE` can select one); only the pinned official kind node image may be pulled (`CONTAINERDESK_K8S_NODE_IMAGE` can override it). Its cleanup targets only the generated Compose project and K8s cluster. Cleanup failures make the run fail, preserve an earlier failure status, and report the exact resources that need inspection.

Use `script/plugin_smoke_test.sh --compose-only` or `--k8s-only` to select one plugin. Both runtime branches passed for this implementation; the script’s read-only service preflight does not start or stop services.
