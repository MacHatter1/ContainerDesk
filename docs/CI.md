# CI and live integration

The `CI / Lint workflows and scripts` job checks workflows with actionlint and shell scripts with ShellCheck using pinned, checksum-verified binaries. The `CI / Test and build` job runs for pull requests and pushes to `main` on GitHub's macOS 26 runner. It uses Xcode 26.6, runs the Swift tests in release configuration with locked package versions, uploads xUnit results, builds the release app bundle and validates it. SwiftPM caches are keyed by the OS, architecture, toolchain and package manifests; they are an acceleration, not a replacement for testing. The tag-triggered release workflow repeats these checks before packaging and publishing. Bundle validation does not establish Developer ID signing or notarization.

Required status checks are configured in the repository’s branch protection, not by workflow files. `main` requires **Test and build** and **Lint workflows and scripts** from GitHub Actions, including for administrators. The live integration workflow is not required. Pull requests exercise both required checks; pushes to `main` also run CI after merging.

## Dedicated live runner

`Live integration` is a manual `workflow_dispatch` on `main`, with no pull request trigger or schedule. It is not a required branch check. The repository currently has no self-hosted runners; an operator must provision one before use. GitHub-hosted Apple silicon runners cannot provide the nested virtualization needed for these checks.

Use a dedicated, trusted Apple silicon Mac and runner account on macOS 26 with Xcode at `/Applications/Xcode_26.6.app`. Register the runner with the `containerdesk-live` label (plus GitHub's `macOS` and `ARM64` labels). Limit repository write access and who can dispatch workflows: a persistent runner can execute code with access to its machine and runtime. The main-only job guard is defense in depth, not a security boundary; a writer can change a workflow on another branch. Review workflow changes before merging, and do not attach the label to a personal or shared workload machine. If the repository later moves to an organization, use [runner group policies](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access) to restrict the group to this workflow on `refs/heads/main`.

Under the runner account, install Apple `container` CLI **1.5.0** at `/opt/homebrew/bin/container`, start its system service and buildkit builder separately, keep at least one dedicated non-sensitive test container running for native read and metrics checks, and cache both `docker.io/library/alpine:3.20` and `alpine:3.20`. The image must have `sh`, `printf`, `cat`, and `sleep`. The workflow checks these prerequisites and does not start, stop, reset, or prune the runtime. The profile check and smoke script create uniquely named resources and request cleanup of only those resources. If a run is forcibly terminated or cleanup fails, an operator must inspect its log and remove only the named resources it created. Concurrency serializes this workflow's runs; it does not lock out other programs, so dedicate the runtime to the runner.

Dispatch **Live integration** from the Actions tab on `main`. The default runs hybrid and cleanup live reads, the profile launch check, and the runtime smoke script in release configuration. The optional `plugins` input requires installed Compose and Kubernetes plugins and cached `redis:7.2.4-alpine` plus the digest-pinned kind node image specified in the workflow. The plugin script uses an isolated kubeconfig and temporary named project and cluster. The optional `mlx` input requires `mlx_lm` 0.32.2 on the runner's PATH and at least one ready compatible model in the runner account's Hugging Face cache. Install and verify these separately; no model is downloaded by the workflow. The live test validates the MLX toolchain and starts and stops its own loopback server.

Only xUnit XML reports are uploaded, retained for seven days; model weights, kubeconfigs and runtime files are not artifacts. Reports and logs can contain diagnostic details, so use a dedicated runner account with no unrelated sensitive workloads. Timeouts or cancellation can interrupt cleanup; check the named resources before another run. See the workflow log for failures. No live test should be dispatched until the runner and its prerequisites are verified.
